Binary Tree Maximum Path Sum

You can follow every step of the solution here. Pick a tree, press Next or click Play, and see how each node computes the best path that peaks at itself, yet returns only a single branch to its parent.

The idea in three steps

  1. 1

    Prune negative branches

    If the best contribution from a subtree is negative, adding that branch to the path makes the sum smaller. With Math.Max(0, Dfs(child)) we clamp negative contributions to zero and ignore them.

  2. 2

    Compare the arch path with the global answer

    At each node, left branch + the node itself + right branch (node.val + left + right) gives the best path whose peak is this node, and it updates _maxSum.

  3. 3

    Return a single branch upward

    When returning to the parent we can't hand over both the left and right branches at once, or the path would fork. Only node.val + Math.Max(left, right) goes upward.

Why is it so efficient?

One visit per node: O(N)

Searching for the best path from scratch at every node would take O(N²). With a bottom-up (postorder) DFS, each node combines the ready-made results from its children in O(1); the total time is O(N).

Arch sum vs. return value

At a node, the arch path node.val + left + right is a valid path. But the parent node can't be added to it, because the path would fork. That is why we return only node.val + Math.Max(left, right) upward.

Why _maxSum = int.MinValue?

All values in the tree can be negative (e.g. [-3]). If we started with _maxSum = 0, we would skip the required non-empty path and wrongly return 0.

Call stack space: O(H)

We keep no extra data structure; only the recursion call stack uses memory proportional to the tree height H (O(log N) for a balanced tree, O(N) in the worst case).
