The idea in three steps

  1. 1

    Think about the last coin used

    If the last coin of the best solution for amount a is coin, then the remaining amount a - coin must also be made with the fewest coins: fewest[a - coin] + 1.

  2. 2

    Fill the table from 0 to amount

    We start with fewest[0] = 0. For every a from 1 to amount, we try all the coins we have and pick the smallest result.

  3. 3

    amount + 1 instead of infinity

    Since the smallest coin is 1, no valid solution can need amount + 1 coins. Using amount + 1 instead of int.MaxValue prevents overflow when you do + 1.

Why is it so efficient?

O(amount × coins.Length) time

Trying every branch recursively would take exponential time. Because the table computes and stores each intermediate amount once, we make only coins.Length comparisons for each a = 1..amount. Memory is just the amount + 1-element array: O(amount).

Why does the greedy approach fail?

In the example coins = [1, 3, 4] and amount = 6, if you start by picking the largest coin you get 4 + 1 + 1, which is 3 coins. Dynamic programming compares both fewest[6 - 4] + 1 = 3 and fewest[6 - 3] + 1 = 2 and finds the 3 + 3 solution (2 coins).

Why amount + 1 and not int.MaxValue?

If the initial value were int.MaxValue, the expression fewest[a - coin] + 1 would overflow into a negative number and mislead Math.Min. amount + 1 both represents "unreachable" and can safely have 1 added to it.

Why the == unreachable check at the end?

If fewest[amount] still holds its initial unreachable value when the loop ends, no combination of the coins could make amount; in that case the problem asks us to return -1.
