Jump Game

You can follow every step of the solution here. Pick an array and press Next or click Play; watch the reachable region grow box by box, and see the moment you reach the end or get stuck.

The idea in three steps

  1. 1

    Track the farthest point, not the paths

    You don't choose which box to jump to from where. You keep just one number: farthest, the farthest box you can reach so far. Every box between 0 and farthest is reachable.

  2. 2

    Extend the boundary at each box

    Walking from left to right, from box i you can get at most as far as box i + nums[i]. If that is farther than farthest, the boundary extends to it.

  3. 3

    If you fall outside the boundary, you're stuck

    If i > farthest, this box cannot be reached from anywhere: false. Once farthest reaches or passes the last box, you are done: true.

Why O(n) time and O(1) memory?

O(n) time

You walk the array at most once and do only a few comparisons at each box. If you reach the end or get stuck early, the loop ends even sooner. The work grows at most in proportion to the length of the array: O(n) time.

O(1) memory

No matter how many elements the array has, you keep only four variables: lastIndex, farthest, i and reach. There is no array recording which boxes are reachable one by one: O(1) memory.

Why are the reachable boxes contiguous?

The number in a box tells you the maximum number of steps you can jump; you can also jump shorter. From a box holding 3 you can move 1, 2 or 3 steps forward. So if you can reach a box, you can also reach every box before it. That is why a single number (farthest) is enough.

Why not always jump as far as possible?

Because the longest jump can be a trap. In [2, 3, 0, 0, 1], if you jump 2 steps from 0 you land on a box holding 0 and get stuck. If you jump 1 step, you reach the end from the box holding 3. This solution never falls into that trap because it doesn't choose jumps; it only tracks the boundary.

Other approaches

Trying every jump from every box works, but the number of paths grows very fast; the 10,000-element array in the tests has about 29998 paths. Storing "is this box reachable?" for each box in an array also works, but needs O(n²) time and O(n) memory. A solution that goes from the end to the start also runs in O(n) time and O(1) memory; the start-to-end method on this page is easier to follow.

Why is there a return false at the end?

The C# compiler wants to see that the method returns a bool on every path. Since it doesn't look at the variables' values, it assumes the loop could finish normally and fall through to the bottom; if you delete this line, the code won't compile. In reality only an empty array gets here, and LeetCode guarantees at least 1 element. Then on the loop's last iteration i equals the last index: either i > farthest and it returns false, or farthest is at least i and it returns true.
