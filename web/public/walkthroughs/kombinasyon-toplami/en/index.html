Combination Sum

Follow the backtracking steps in a decision tree where the same number can be picked any number of times, and see how the start index prevents duplicate permutations.

The idea in three steps

  1. 1

    Pick a candidate and subtract it from the target

    At each step we add candidates[i] to the path list and update the remaining target to remaining - candidates[i].

  2. 2

    Keep the index fixed to pick again

    To be able to use the same number any number of times, we pass i instead of i + 1 to the recursive call; but we never try the indices before i again.

  3. 3

    Reach the target or prune and backtrack

    If remaining == 0, we record the current combination. When remaining < 0, we prune the branch and remove the last element.

Why is it so efficient?

Why don't duplicate permutations appear?

If we started the loop from 0 at every step, besides [2, 2, 3] we would also produce other orderings of the same combination, such as [2, 3, 2] and [3, 2, 2]. Thanks to the start parameter, the next step never goes back to an earlier candidate.

Why is Backtrack(i, ...) called?

Since each element can be picked any number of times, after choosing the candidate at index i the recursive call continues from index i again. When we return from that branch, the loop moves to the next candidate with i++, which means giving up that element.

Early pruning

Once the sum exceeds the target (remaining < 0), going deeper only makes the sum larger (because all candidates are positive). So we cut the branch right away with return and avoid needless searching.

A copying detail: new List<int>(path)

The path list is shared as a single reference throughout the search and keeps changing. When a result is found, we must create a new copy to freeze its current state and add that to result.
