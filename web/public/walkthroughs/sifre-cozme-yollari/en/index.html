Decode Ways

Follow step by step how we scan the digit string from right to left and, at each position, add up the number of ways for the valid one-digit (1–9) and two-digit (10–26) letter choices.

The idea in three steps

  1. 1

    A zero can't be decoded on its own

    If a suffix starts with '0', it can't produce a valid letter; the number of ways at that position is simply 0.

  2. 2

    One digit: dp[i + 1]

    If the digit s[i] is between 1..9, it is split off as a single letter and you take the number of ways for the remaining suffix (next1).

  3. 3

    Two digits: + dp[i + 2]

    If the two digits s[i..i+2] are between 10..26, together they can form one letter; the number of ways from two positions ahead (next2) is added.

Why is it so efficient?

The subproblems overlap

If we branched recursively into one-digit and two-digit choices at every position, we would compute the same suffixes over and over and the running time would grow to O(2ⁿ). In a single right-to-left pass, each suffix is computed only once: O(n) time.

Only the last two states are needed

Just like in the Fibonacci sequence, dp[i] only looks at dp[i + 1] and dp[i + 2]. Instead of storing the whole array, we shift the next1 and next2 variables and use O(1) extra memory.

Why is '0' handled specially?

'0' doesn't map to a letter on its own; it is only valid as the second digit in "10" or "20". Going from right to left, when s[i] == '0', current = 0 is assigned, and the '1' or '2' to its left picks it up correctly through next2.

How is the 26 limit checked?

For the two-digit number to be between 10..26, either the first digit must be '1' (10..19), or the first digit must be '2' and the second at most '6' (20..26). This way there is no need to call int.Parse.
