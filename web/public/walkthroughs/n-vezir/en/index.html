N-Queens

Step through how, as queens are placed row by row, the cols, posDiag (r + c), and negDiag (r - c) sets catch conflicts instantly, and how the search backtracks out of dead ends.

The idea in three steps

  1. 1

    Exactly one queen per row

    Two queens can't share a row. Running the search row by row from r = 0 to n - 1 rules out row conflicts from the start.

  2. 2

    Encode the diagonals with math

    On a diagonal running from top-right to bottom-left, the sum r + c stays the same; on a diagonal running from top-left to bottom-right, the difference r - c stays the same. Three HashSets give an O(1) check.

  3. 3

    At a dead end, undo and continue

    When no valid column is left in the next row, we remove the queen from the board and the sets (backtrack) and try the next column in the current row.

Why is it so efficient?

Early pruning instead of brute force

Placing n queens arbitrarily on an n x n board produces C(n², n) combinations. Going row by row and pruning the subtree at the first conflict eliminates millions of invalid branches without ever visiting them.

O(1) conflict check

Scanning the earlier queens on the board one by one for every square would take O(n). By keeping the c, r + c, and r - c values in sets, we learn whether a square is safe in a single step.

Why do r + c and r - c work?

When you move one step from top-right toward bottom-left, r goes up by 1 and c goes down by 1, so the sum r + c stays constant. When you move from top-left toward bottom-right, both go up by 1, so the difference r - c stays constant.

In-place search on a single board

Instead of copying a new char[][] at every step, we set board[r][c] = 'Q' on a single board and change it back to '.' on the way back. A copy of the board is taken only when r == n.
