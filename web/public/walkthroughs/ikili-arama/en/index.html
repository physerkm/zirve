Binary Search

In a sorted array, we look at the middle element (nums[mid]) and discard half of the search range with a single comparison. Watch how the [left, right] range shrinks at every step.

The idea in three steps

  1. 1

    Look at the middle element

    We find the middle index of the active search range [left, right] with mid = left + (right - left) / 2.

  2. 2

    Discard the wrong half entirely

    Since the array is sorted, if nums[mid] < target, the target can't be in the left half (left = mid + 1); if it's greater, the target can't be in the right half (right = mid - 1).

  3. 3

    Find it or exhaust the range

    When nums[mid] == target, we return the index. If left > right, the range is empty; the target isn't in the array (-1).

Why is it so efficient?

It halves at every step: O(log n) time

In an array of 1,000,000 elements, a linear search takes 1,000,000 steps in the worst case, while binary search halves the range at every step and reaches the result in at most 20 steps.

Why the difference formula instead of (left + right) / 2?

In very large arrays, the sum left + right can exceed int.MaxValue and overflow into a negative number. left + (right - left) / 2 gives the same midpoint mathematically, with no risk of overflow.

Why mid + 1 and mid - 1?

We've already checked that nums[mid] != target; the index mid itself is no longer a candidate. If we didn't remove it from the range, the loop would get stuck in the same place forever once left == right.

O(1) extra space

Instead of building a recursive call stack, we keep only three index variables (left, right, mid), so the space complexity is O(1).
